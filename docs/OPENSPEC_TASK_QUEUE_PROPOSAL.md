# OpenSpec 规格提案：任务队列系统深度修复

## 规格信息
- **提案ID**: SPEC-2025-001
- **项目**: 合同审查SaaS系统
- **创建时间**: 2025-12-11
- **状态**: 待审批
- **优先级**: Critical (P0)

## 问题分析

### 1. 核心问题描述

#### 1.1 系统架构问题
- **GitHub Actions未同步**: 本地有4个领先提交未推送到远程仓库
- **任务队列瘫痪**: 僵尸任务卡住整个处理流程
- **单点故障**: 原始Task Runner设计为单线程处理
- **缺乏监控**: 无法及时发现和诊断问题

#### 1.2 技术债务分析
- **数据库设计缺陷**: 缺少分布式锁、超时机制、工作节点标识
- **错误处理不足**: 重试机制简单，缺乏智能退避策略
- **配置管理混乱**: 环境变量配置不完整，缺少关键配置
- **版本控制问题**: 修复方案未正确部署到生产环境

#### 1.3 业务影响
- **用户体验**: 合同处理功能完全不可用
- **数据安全**: 积压的合同文件可能存在泄露风险
- **系统稳定性**: 长期运行可能导致系统崩溃

### 2. 根本原因分析

#### 2.1 设计层面根本原因
1. **单体架构思维**: 将分布式任务处理简化为单次调用
2. **缺乏容错设计**: 没有考虑故障恢复和自愈能力
3. **监控盲区**: 缺乏可观测性设计

#### 2.2 实施层面根本原因
1. **配置同步失败**: GitHub Actions配置未正确更新
2. **环境变量缺失**: TASK_RUNNER_TOKEN等关键配置未设置
3. **部署流程不完整**: 数据库迁移和函数部署未同步执行

#### 2.3 流程层面根本原因
1. **缺乏验证机制**: 部署后没有有效的健康检查
2. **回滚策略缺失**: 出现问题时无法快速恢复服务
3. **文档不完整**: 缺乏详细的操作手册和应急预案

### 3. 技术风险评估

#### 3.1 高风险项目
- **数据丢失风险**: 僵尸任务可能包含重要合同数据
- **服务中断风险**: 完全部署可能影响现有功能
- **安全风险**: 配置不当可能导致未授权访问

#### 3.2 依赖关系分析
- **Supabase服务**: 依赖云服务稳定性
- **OCR服务**: 依赖外部AI服务的可用性
- **Vercel部署**: 依赖CI/CD管道的正确配置

## 解决方案规格

### 4. 整体修复策略

#### 4.1 三阶段修复方案
**阶段1: 紧急修复 (0-4小时)**
- 立即修复僵尸任务
- 恢复基本的任务处理功能
- 确保系统可用性

**阶段2: 系统升级 (1-2天)**
- 部署分布式任务处理系统
- 升级GitHub Actions配置
- 实施监控和告警

**阶段3: 长期优化 (1周)**
- 性能调优和扩展性改进
- 完善监控和运维工具
- 建立最佳实践文档

#### 4.2 技术架构升级
1. **从单点到分布式**: 支持多worker并行处理
2. **从脆弱到容错**: 实现自动故障检测和恢复
3. **从黑盒到透明**: 全面的监控和日志记录

### 5. 具体技术规格

#### 5.1 数据库改进规格
```sql
-- 新增字段规格
- timeout_at: timestamptz -- 任务超时时间
- worker_id: text -- 处理节点标识
- started_at: timestamptz -- 开始处理时间
- priority: integer DEFAULT 5 -- 任务优先级 (1-10)

-- 新增函数规格
- fetch_queued_tasks(): 分布式获取任务
- check_task_timeouts(): 检查超时任务
- retry_failed_tasks(): 重试失败任务
- cleanup_old_tasks(): 清理历史数据
```

#### 5.2 应用程序规格
```typescript
// Task Runner v2 规格要求
interface TaskRunnerV2 {
  // 批量处理能力
  batchSize: number; // 默认3个并行
  workerTimeout: number; // 默认10分钟

  // 健康检查接口
  healthCheck(): Promise<HealthStatus>;

  // 维护模式
  maintenanceMode(): Promise<MaintenanceResult>;

  // 指标收集
  recordMetrics(metrics: TaskMetrics): Promise<void>;
}
```

#### 5.3 CI/CD规格升级
```yaml
# GitHub Actions规格要求
- 多worker并行处理 (3个并行实例)
- 健康检查和故障转移
- 定时维护任务 (每小时)
- 深度清理任务 (每天)
- 执行监控和报告
- 错误通知机制
```

### 6. 配置管理规格

#### 6.1 环境变量规格
```bash
# 新增必需配置
TASK_BATCH_SIZE=3              # 每批处理任务数量
TASK_TIMEOUT_MINUTES=10        # 任务超时时间
TASK_MAX_ATTEMPTS=3            # 最大重试次数

# 关键缺失配置
TASK_RUNNER_TOKEN=xxx          # GitHub Actions认证令牌
PROJECT_SERVICE_ROLE_KEY=xxx   # Supabase服务角色密钥
```

#### 6.2 秘密管理规格
- **GitHub Secrets**: 配置TASK_RUNNER_TOKEN
- **Supabase Secrets**: 验证所有环境变量完整性
- **Vercel Environment**: 同步生产环境配置

### 7. 监控和验证规格

#### 7.1 关键指标规格
- **吞吐量**: 每分钟处理任务数 > 1个/分钟
- **成功率**: 任务完成百分比 > 95%
- **延迟**: 任务平均处理时间 < 5分钟
- **可用性**: 系统可用性 > 99.9%

#### 7.2 告警阈值规格
- 任务积压 > 10个时告警
- 失败率 > 10%时告警
- 处理延迟 > 15分钟时告警
- Worker离线 > 5分钟时告警

#### 7.3 验证清单规格
```markdown

- [ ] 新任务可以正常处理

```

### 8. 风险缓解策略

#### 8.1 技术风险缓解
- **回滚计划**: 保留原始workflow作为备份
- **灰度部署**: 先在开发环境验证，再部署生产
- **监控优先**: 部署前先确保监控系统可用

#### 8.2 业务风险缓解
- **数据备份**: 部署前完整备份任务数据
- **服务窗口**: 选择低流量时间进行部署
- **用户通知**: 提前通知用户可能的维护窗口

#### 8.3 运维风险缓解
- **文档更新**: 详细记录操作步骤和应急预案
- **团队培训**: 确保运维团队了解新系统
- **支持准备**: 准备7x24小时技术支持
